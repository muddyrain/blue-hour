# 保存、旧档与失败恢复

内容基线 `edf9bd9`，正式 schema 为 **v5**。此页面描述 Blue Hour 自身的营地保存，不是原作存档格式或完整崩溃恢复系统。

## 何时会保存

- 正常撤离后，点击“返回营地”提交一次结果。
- 在营地确认呼号、维修或配装等持久化修改。
- 声音设置需要独立显式保存。

当前日数、钱粮、生命、已结算身份、武器与归属、个人战绩和行动记录按营地边界保存。出击中途、结果尚未回营、练习、镜头和威胁状态不保存。退出后恢复最近成功保存的营地，不能恢复到上次局内坐标。

进度采用 `user://saves/run.json`，有效备份为同目录 `run.json.bak`；声音为 `user://settings/audio.json`。`user://` 由引擎解析为本机用户数据位置，不在仓库内保存正式玩家进度。

## 继续、新游戏与旧版

有已有进度先点“继续游戏”。新游戏遇到旧档会先确认，取消不改旧文件。读取 v1–v4 先在内存迁移；首次写新版前保留有效旧主档及不同的有效备份原字节。

v4 到 v5 只补未知成长字段和空行动明细，保留旧呼号、伤情、资源、战绩、库存和配装，不回填历史经验或事件。旧 v4 程序不能读取 v5，继续已有旅程应使用本版或兼容新版，旧原件仍单独保留。

## 坏档和写入失败

主档不合法时阻止不安全出击，给出错误；存在有效备份时由玩家明确选择，不静默覆盖坏原件。未知版本、非法身份或库存关系不能靠猜测修补后继续。

保存失败会明确提示，并可在营地重试。已计算的同一结果不因重试再次奖励、扣粮或推进日期；退出前应确认成功保存。保护主档和备份的替换边界由真实文件系统检查覆盖，但这不等于所有设备上的断电保证。

## 当前限制

此快照仍以原双人正式旅程为边界。没有多槽位、云同步、局内致死检查点、崩溃后重建整个行动或所有并发写者保证；技术异常也没有被统一解释为玩家主动放弃。正式永久死亡和未来迁移另行设计，旧零 HP 不自动变成永久死亡。

自动化检查使用 `tests/fixtures` 中的合成 Blue Hour 旧版状态和独立测试目录，不读取参考原作或正式玩家数据。后续变更必须在新候选上重新执行检查，不能把历史内部包的结果算成本次通过。
